Enhancement One Narrative: Software Design and Engineering

Artifact Description

The artifact I selected for this enhancement is the Grazioso Salvare Rescue Animal Dashboard that I originally created for CS 340 Client/Server Development. The project was built around animal shelter data from the Austin Animal Center and used Python, MongoDB, Pandas, Dash, Plotly, and Dash Leaflet. The dashboard allows a user to view animal records, select different rescue categories, sort and filter the data table, view the breeds represented in the current results, and display the location of a selected animal on a map.

The original project was created earlier in my Computer Science program as a client/server application. It connected a Python dashboard to MongoDB through an AnimalShelter CRUD class. At the time, most of the dashboard logic was contained in a Jupyter notebook. The project worked and met the requirements of the original course, but reviewing it again for the capstone showed several areas where the design could be improved.

Why I Selected This Artifact and How It Was Improved

I selected this artifact because it includes several parts of software development in one project instead of only demonstrating one isolated skill. It has a user interface, database access, data processing, filtering, and visualizations. This made it a good artifact for showing how my approach to software design has changed since I originally completed CS 340. It also gave me an opportunity to improve existing code instead of starting over with a completely new project.

The biggest improvement was reorganizing the project so that the dashboard notebook was no longer responsible for almost everything. I moved the rescue-filter query logic into a separate rescue_filters.py module and moved the breed chart and animal map creation into visualization.py. The AnimalShelter class remains responsible for database access, while the notebook is mainly responsible for the interface and callbacks. This separation makes the program easier to read and makes individual pieces easier to change or test without having to work through the entire notebook.

I also modernized the application by replacing the deprecated JupyterDash approach with the current Dash application structure. During the enhancement, I added validation and error handling around the initial database load, dashboard filtering, breed chart, and map. For example, the map now checks whether a selected animal has usable latitude and longitude information instead of assuming that every record contains valid coordinates. The dashboard can also handle an empty database result without immediately failing.

Another important improvement involved security. The original project stored MongoDB connection information directly in the source code. I changed the project so that connection settings are loaded from environment variables in a .env file and added that file to .gitignore. I also ignored Python, Jupyter, and pytest cache files so that temporary files and credentials are not included in source control.

Finally, I added automated tests for the rescue-filter logic using pytest. The test file checks all three rescue categories, the Reset option, and an unknown filter value. All five tests pass. Separating the filter logic into its own module made these tests possible without launching the dashboard or connecting to MongoDB. This was a useful example of how software organization affects testability as well as readability.

Course Outcome Coverage

The enhancement met the main course outcomes that I planned to address for the software design and engineering category. The strongest connection is to the outcome involving the use of well-founded techniques, skills, and tools to create computing solutions that provide value. Refactoring the project into separate modules, modernizing the Dash code, adding exception handling, and introducing automated tests all improved the maintainability and reliability of the application instead of only changing how it looks.

The enhancement also made progress toward the security outcome. Moving database credentials out of the source code was a direct response to a weakness in the original design. Using environment variables and preventing the .env file from being committed demonstrates a more security-focused approach to configuration and source control. Error handling also helps prevent the application from exposing unnecessary technical details to a user when something goes wrong.

There is also some progress toward the outcome involving the design and evaluation of computing solutions because I had to make decisions about where different responsibilities should exist in the application and then verify those decisions through testing. I do not consider this enhancement the main demonstration of my algorithms and data structures skills, however. I plan to demonstrate that outcome more directly in the next enhancement through the rescue-candidate scoring and ranking system. Because of that, I do not need to make a major change to my original outcome-coverage plan at this time.

Reflection on the Enhancement Process

Working on this enhancement showed me that improving an existing program can be more challenging than adding a new feature. I wanted to change the structure of the project without breaking the dashboard functions that already worked. Because of this, I made the changes in smaller steps and tested the dashboard after each major change. I checked all four filter options, the breed chart, and the map as the code was moved into separate modules. This helped me identify problems close to the change that caused them instead of trying to debug several changes at once.

One challenge was updating the older dashboard code. The original project used JupyterDash, and the current environment no longer supported the old run_server approach in the same way. Updating the project to use Dash allowed the application to run again while also removing a deprecated dependency from the design. I also encountered a duplicate callback problem while moving the map code into the visualization module. That issue came from an older callback decorator that was still left in the notebook. Finding and removing it reinforced the importance of checking the surrounding code during a refactor instead of assuming that moving a function is the only change required.

The testing portion was another useful part of the process. Before this enhancement, the rescue queries were embedded in the dashboard callback, which made them harder to test independently. After moving them into get_rescue_query(), I could write simple pytest tests that directly checked the MongoDB query produced by each option. Seeing all five tests pass gave me more confidence that the refactoring had preserved the original filter behavior.

Overall, this enhancement helped me understand that software engineering is not only about making code work. Structure, maintainability, security, error handling, and testing all affect the quality of a program. The enhanced dashboard still performs the same main job as the original artifact, but its internal design is easier to understand and gives me a better foundation for the algorithms and database enhancements that I will complete later in the capstone.
