1. Briefly describe the artifact. What is it? When was it created?

The artifact I selected is the Grazioso Salvare Rescue Animal Dashboard that I originally created for CS 340: Client/Server Development. The project uses Python, Dash, MongoDB, PyMongo, Pandas, Plotly, and Dash Leaflet to work with animal shelter records from the Austin Animal Center dataset. The original dashboard allowed a user to filter animal records by rescue type, view breed information, and display the location of a selected animal on an interactive map.

I chose this project for my CS 499 capstone because it already combines several areas of computer science and gave me a good foundation for all three required enhancements. The database portion was especially useful because MongoDB was already responsible for storing and retrieving the animal records, which gave me an opportunity to improve how the application used the database instead of replacing it entirely.

2. Justify the inclusion of the artifact. How was the artifact improved?

I included this artifact in my ePortfolio because it demonstrates programming, database interaction, data processing, visualization, testing, and application design. It also gave me an opportunity to take an older project and improve it instead of only presenting the original version.

For the database enhancement, I expanded the AnimalShelter database layer with MongoDB aggregation and index management. The new aggregation functionality allows the application to calculate breed counts in MongoDB using a pipeline that matches records, groups them by breed, and sorts the results by count. The dashboard's breed chart now uses those MongoDB aggregation results instead of relying entirely on Pandas to calculate the breed distribution after retrieving the records.

I also added database indexes for fields commonly used by the application's rescue queries, including animal type, breed, sex upon outcome, and age upon outcome in weeks. I added functionality to inspect the indexes rather than automatically changing the database every time the application starts. This keeps normal dashboard operation separate from database administration.

The database changes were tested with mocked MongoDB interactions. This allowed me to test aggregation, index creation, and index inspection without making unnecessary changes to the actual animal shelter database. The complete automated test suite now has 30 passing tests across filtering, candidate scoring, visualization, and database behavior.

4. Reflect on the process of enhancing and modifying the artifact. What did you learn? What challenges did you face?

The main thing I learned from this enhancement was that database performance is not only about making a query work. It is also about deciding where processing should happen and how the database can be used effectively. In the original application, much of the breed processing happened after records were retrieved into Python. Moving the grouping and counting into a MongoDB aggregation pipeline made better use of the database itself.

I also learned more about indexing and the trade-off between application simplicity and database performance. I considered having the application automatically create indexes every time it started, but decided that database administration should remain separate from normal dashboard startup. Instead, the project has explicit methods for creating and inspecting indexes. This makes the behavior easier to understand and avoids unnecessary database changes whenever the application runs.

Testing was another important part of the process. I added database tests using mocked MongoDB operations so aggregation and index behavior could be verified without modifying the real database. The project now has 30 automated tests, and I also manually tested the dashboard after the aggregation was connected to the visualization. All four rescue-type options continued to work, the breed chart updated correctly, and the map continued to function.

One challenge was making the new database processing work with the existing dashboard without changing behavior users already relied on. I did not want the new aggregation to accidentally display breed counts for the entire database when a specific rescue category was selected. The solution was to use the animal IDs from the current dashboard results as the criteria for the MongoDB aggregation. This allowed the database to perform the aggregation while keeping the chart connected to the records currently being displayed.

Overall, this enhancement showed me that improving an existing application requires more than adding new code. I had to understand how the existing pieces worked together, make changes without breaking them, and test the results at both the individual method and full-application levels. That experience is useful for the type of software and cybersecurity work I hope to pursue after completing my degree.
